🚀 Repository Setup and Cloning

▼

Essential commands for setting up repositories, cloning existing projects, and configuring Git for the first time. These are the foundational operations for any Git workflow.

Initial Setup and Configuration

# Global Git configuration (one-time setup)
git config --global user.name "Your Name"
git config --global user.email "your.email@company.com"

# Set default branch name
git config --global init.defaultBranch main

# Configure line ending preferences (important for cross-platform teams)
git config --global core.autocrlf true    # Windows
git config --global core.autocrlf input   # macOS/Linux

# Set default editor
git config --global core.editor "code --wait"  # VS Code
git config --global core.editor "vim"          # Vim

# View current configuration
git config --list
git config --global --list
  • What it does: Sets up your Git identity and preferences globally
  • When to use: First time setting up Git on a new machine
  • Important: Use your work email for work repositories
  • Line endings: Prevents issues when working across different operating systems

Creating and Cloning Repositories

# Initialize a new repository in current directory
git init

# Initialize with specific branch name
git init --initial-branch=main

# Clone a remote repository
git clone https://github.com/username/repository.git

# Clone with a different local name
git clone https://github.com/username/repository.git my-local-name

# Clone only a specific branch
git clone -b feature-branch https://github.com/username/repository.git

# Shallow clone (faster for large repos, only recent history)
git clone --depth=1 https://github.com/username/repository.git

# Clone with submodules
git clone --recurse-submodules https://github.com/username/repository.git
  • git clone: Creates a complete copy of a remote repository locally
  • Shallow clone: Faster download but limited history (good for CI/CD)
  • Branch-specific clone: Only downloads specified branch
  • Submodules: Downloads nested repositories within the main project

📝 Basic Git Workflow

▼

The fundamental Git workflow: staging changes, creating commits, and viewing repository status. These commands form the core of daily Git usage for tracking and saving changes.

Staging and Committing Changes

# Check repository status - see what files have changed
git status

# See detailed differences in files
git diff              # Unstaged changes
git diff --staged     # Staged changes
git diff HEAD         # All changes since last commit

# Stage files for commit
git add filename.py              # Add specific file
git add src/                     # Add entire directory
git add *.py                     # Add all Python files
git add .                        # Add all changes in current directory
git add -A                       # Add all changes in repository

# Interactively stage parts of files
git add -p filename.py           # Review and stage chunks individually

# Unstage files (remove from staging area)
git reset filename.py            # Unstage specific file
git reset                        # Unstage all files

# Commit staged changes
git commit -m "Add data processing pipeline"

# Commit with detailed message
git commit -m "Add ETL pipeline

- Implemented bronze layer data ingestion
- Added data quality validation
- Created unit tests for transformations"

# Stage and commit in one command (only for tracked files)
git commit -am "Quick fix for null handling"
  • git status: Shows current state - modified, staged, and untracked files
  • git add: Moves changes from working directory to staging area
  • git commit: Saves staged changes permanently with a message
  • Staging area: Allows you to craft precise commits with only desired changes

Viewing History and Changes

# View commit history
git log                          # Full commit history
git log --oneline                # Condensed one-line per commit
git log --graph --decorate --all # Visual branch representation
git log -p                       # Show actual changes in each commit
git log --stat                   # Show file statistics for each commit

# View history for specific file
git log filename.py
git log --follow filename.py     # Follow renames

# View specific commit
git show commit-hash
git show HEAD                    # Show latest commit
git show HEAD~1                  # Show previous commit

# View changes between commits
git diff commit1..commit2
git diff HEAD~2..HEAD           # Last 2 commits

# View who modified each line of a file
git blame filename.py

# Search commit messages
git log --grep="bug fix"
git log --author="John Doe"
git log --since="2024-01-01"
  • git log: Shows commit history with various formatting options
  • git show: Displays detailed information about specific commits
  • git blame: Shows who last modified each line (useful for debugging)
  • Filtering: Search commits by author, date, or message content

🌿 Branch Management

▼

Working with branches for parallel development, feature isolation, and collaborative workflows. Branching is essential for managing multiple features and maintaining stable code.

Creating and Switching Branches

# List all branches
git branch                       # Local branches only
git branch -a                    # All branches (local and remote)
git branch -r                    # Remote branches only

# Create new branch
git branch feature-new-pipeline

# Create and switch to new branch
git checkout -b feature-new-pipeline
git switch -c feature-new-pipeline    # Modern alternative

# Switch between branches
git checkout main
git switch main                  # Modern alternative

# Switch to previous branch
git checkout -
git switch -

# Create branch from specific commit
git checkout -b hotfix abc1234

# Create branch from remote branch
git checkout -b local-branch origin/remote-branch
  • Branches: Allow parallel development without affecting main codebase
  • git switch: New command specifically for switching branches (clearer than checkout)
  • Feature branches: Create separate branches for each feature or bug fix
  • Branch from commit: Useful for creating hotfixes from specific points

Merging and Branch Management

# Merge branch into current branch
git merge feature-branch

# Create merge commit even if fast-forward is possible
git merge --no-ff feature-branch

# Merge with custom commit message
git merge feature-branch -m "Integrate new ETL pipeline"

# Delete local branch (safe - prevents deletion if not merged)
git branch -d feature-branch

# Force delete local branch
git branch -D feature-branch

# Delete remote branch
git push origin --delete feature-branch

# Rename current branch
git branch -m new-branch-name

# Track remote branch
git branch --set-upstream-to=origin/main main

# List merged branches
git branch --merged
git branch --no-merged           # Branches not yet merged
  • git merge: Integrates changes from one branch into another
  • --no-ff: Creates explicit merge commit for better history
  • Safe deletion: -d prevents deletion of unmerged branches
  • Branch tracking: Links local branches to remote counterparts

🔄 Remote Repository Operations

▼

Working with remote repositories for collaboration, synchronization, and backup. Essential for team workflows and sharing code across different environments.

Push, Pull, and Fetch Operations

# Add remote repository
git remote add origin https://github.com/username/repo.git

# List remote repositories
git remote -v

# Fetch changes from remote (doesn't merge)
git fetch origin
git fetch --all                  # Fetch from all remotes

# Pull changes from remote (fetch + merge)
git pull origin main
git pull                         # Pull from tracked branch

# Pull with rebase instead of merge
git pull --rebase origin main

# Push changes to remote
git push origin main
git push                         # Push to tracked branch

# Push new branch to remote
git push -u origin feature-branch    # -u sets up tracking

# Push all branches
git push --all origin

# Push tags
git push --tags

# Force push (use carefully!)
git push --force-with-lease origin main  # Safer than --force
git push --force origin main             # Dangerous - can overwrite work
  • git fetch: Downloads changes but doesn't merge them
  • git pull: Combines fetch and merge in one operation
  • git push: Uploads local changes to remote repository
  • --force-with-lease: Safer force push that checks for remote changes

Managing Remote Branches

# List remote branches
git ls-remote origin

# Track remote branch locally
git checkout --track origin/feature-branch

# Update remote branch references
git remote prune origin          # Remove stale remote branch references

# Change remote URL
git remote set-url origin https://github.com/newusername/repo.git

# Add multiple remotes (useful for forks)
git remote add upstream https://github.com/original/repo.git
git remote add fork https://github.com/yourfork/repo.git

# Fetch from upstream and merge into local
git fetch upstream
git checkout main
git merge upstream/main
git push origin main             # Update your fork
  • Remote tracking: Links local branches to remote counterparts
  • Pruning: Cleans up references to deleted remote branches
  • Multiple remotes: Useful for managing forks and upstream repositories
  • Upstream workflow: Keep forks synchronized with original repository

🔄 Rebase and Advanced History

▼

Advanced Git operations for rewriting history, cleaning up commits, and maintaining a linear project history. Use these carefully, especially on shared branches.

Interactive Rebase

# Rebase current branch onto main
git rebase main

# Interactive rebase to edit last 3 commits
git rebase -i HEAD~3

# Interactive rebase from specific commit
git rebase -i commit-hash

# Continue rebase after resolving conflicts
git rebase --continue

# Abort rebase and return to original state
git rebase --abort

# Skip current commit during rebase
git rebase --skip
  • Rebase: Moves commits to a new base, creating linear history
  • Interactive rebase: Allows editing, squashing, or reordering commits
  • Conflict resolution: May require manual conflict resolution
  • History rewriting: Changes commit hashes - be careful with shared branches

Undoing Changes

# Undo last commit (keep changes in working directory)
git reset HEAD~1

# Undo last commit (keep changes staged)
git reset --soft HEAD~1

# Undo last commit (discard changes completely)
git reset --hard HEAD~1

# Revert a commit (create new commit that undoes changes)
git revert commit-hash

# Revert merge commit
git revert -m 1 merge-commit-hash

# Restore file to last committed version
git restore filename.py
git checkout HEAD -- filename.py

# Restore file from specific commit
git restore --source=commit-hash filename.py

# Create new commit that undoes changes in working directory
git commit -a --amend            # Modify last commit
  • git reset: Moves HEAD pointer, can discard commits and changes
  • git revert: Safely undoes changes by creating new commits
  • git restore: New command for restoring files (clearer than checkout)
  • --amend: Modify the most recent commit message or content

🎯 Pull Requests and Collaboration

▼

Best practices for creating pull requests, code reviews, and collaborative development workflows using GitHub, GitLab, or similar platforms.

Pull Request Workflow

# Typical feature development workflow

# 1. Start from main branch
git checkout main
git pull origin main

# 2. Create feature branch
git checkout -b feature/add-data-validation

# 3. Make changes and commit
git add .
git commit -m "Add comprehensive data validation

- Implement null value checks
- Add data type validation  
- Create unit tests for validation functions
- Update documentation"

# 4. Push branch to remote
git push -u origin feature/add-data-validation

# 5. Create pull request via web interface or CLI
gh pr create --title "Add comprehensive data validation" \
             --body "This PR adds robust data validation including null checks and type validation"

# 6. After review, update based on feedback
git add .
git commit -m "Address code review feedback"
git push origin feature/add-data-validation

# 7. After PR approval and merge, cleanup
git checkout main
git pull origin main
git branch -d feature/add-data-validation
  • Feature branches: Isolate development work from main branch
  • Descriptive commits: Clear commit messages help reviewers understand changes
  • Pull request description: Explain the purpose and scope of changes
  • Cleanup: Delete feature branches after successful merge

Code Review Best Practices

# Reviewing someone else's pull request

# 1. Fetch the latest changes
git fetch origin

# 2. Check out the PR branch locally
git checkout feature/other-persons-branch

# 3. Test the changes locally
python -m pytest tests/
python main.py --dry-run

# 4. Review the diff
git diff main...feature/other-persons-branch

# 5. Leave feedback via web interface

# Updating your PR based on review feedback
# Make changes locally, then:
git add .
git commit -m "Fix linting issues and add error handling"
git push origin feature/add-data-validation

# Squash commits before merge (optional)
git rebase -i main
# In interactive rebase, squash commits together
git push --force-with-lease origin feature/add-data-validation
  • Local testing: Always test PR changes locally before reviewing
  • Constructive feedback: Provide specific, actionable review comments
  • Iterative improvement: Address feedback in additional commits
  • Squashing: Clean up commit history before merging (optional)

📋 Git Workflow Summary

▼
  • Start with main: Always begin new work from updated main branch
  • Feature branches: Create separate branches for each feature or fix
  • Frequent commits: Make small, logical commits with clear messages
  • Regular synchronization: Fetch and merge upstream changes frequently
  • Code review: Use pull requests for collaborative code review
  • Clean history: Consider squashing commits before merging
  • Backup: Push branches regularly to avoid losing work
  • Security: Never commit secrets or credentials
